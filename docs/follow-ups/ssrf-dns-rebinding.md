## SSRF 가드가 DNS rebinding으로 우회될 수 있음

**증상**: `lib/feedme/url-safety.ts`의 `assertPublicHost()`는 `dns.lookup()`으로 호스트네임을 조회해 사설/루프백/링크로컬 주소인지 검사하지만, 이후 `lib/feedme/convert.ts`의 `fetch(currentUrl)`은 Node(undici)가 별도로 다시 DNS를 조회한다.

**관찰된 근거**: 코드 리뷰(`code-review low`, task 01의 리뷰 체크포인트 대상 범위)에서 확인. 두 조회 시점이 분리되어 있어, 검증-사용 시점 불일치(TOCTOU)가 존재함을 코드로 확인했다. 실제 공격 재현은 하지 않음(공격자가 통제하는 짧은 TTL의 DNS 인프라가 필요해 일반적인 사용 경로로는 재현되지 않음).

**의심되는 원인**: 짧은 TTL의 DNS 레코드를 운영하는 공격자가, `assertPublicHost()`가 조회하는 시점에는 공인 IP를 반환하고, 그 직후 `fetch()`가 실제 커넥션을 맺는 시점에는 사설/루프백 IP로 응답을 바꾸면(DNS rebinding) 검증을 통과한 뒤 내부망으로 요청이 전송될 수 있다.

**시도한 것**: 스킴 검증(http/https만 허용), 리다이렉트 수동 처리 + 매 hop 재검증, 응답 크기 제한은 구현하고 curl로 직접 검증함(127.0.0.1, 169.254.169.254, 192.168.1.1, 잘못된 스킴 모두 차단). 단, 조회한 IP로 직접 커넥션을 맺는 방식(예: `dns.lookup`으로 얻은 IP를 `fetch`에 강제하고 Host 헤더만 원래 호스트명으로 보내는 방식)은 이번 작업 범위를 벗어난다고 판단해 구현하지 않음.

**제안하는 다음 단계**: 조회한 IP를 커넥션 대상으로 고정(pin)하고 TLS SNI/Host 헤더만 원래 호스트명을 사용하도록 `fetch`의 dispatcher(undici Agent)를 커스터마이징하거나, 아웃바운드 요청을 격리된 네트워크 정책(예: 사설 대역으로 나가는 아웃바운드 트래픽을 인프라 레벨에서 차단)으로 방어하는 방안을 검토.
