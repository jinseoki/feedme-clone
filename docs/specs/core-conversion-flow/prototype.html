2년 전, 우리는 트래픽이 늘어난다는 이유만으로 하나였던 서비스를 11개의 마이크로서비스로 쪼갰다. 결과부터 말하면, 지난 분기에 그중 7개를 다시 하나의 코드베이스로 합쳤다. 이 글은 그 과정에서 무엇을 놓쳤는지에 대한 기록이다.

1. 배포는 빨라졌지만, 디버깅은 3배 느려졌다

서비스를 나누고 나서 각 팀은 독립적으로 배포할 수 있게 됐다. 하지만 요청 하나가 실패했을 때, 그 원인을 찾으려면 최소 4개 서비스의 로그를 순서대로 대조해야 했다. 온콜 대응 시간은 평균 12분에서 41분으로 늘었다.

// 실제로 겪었던 장애의 원인
// order-service -> inventory-service -> payment-service 사이의
// 타임아웃 설정이 서로 달라서 생긴 연쇄 실패
order-service: timeout 3000ms
inventory-service: timeout 5000ms
payment-service: timeout 2000ms

2. 트랜잭션 경계가 코드에서 네트워크로 옮겨갔다

모놀리스에서는 데이터베이스 트랜잭션 하나로 끝났을 일이, 마이크로서비스에서는 사가(Saga) 패턴과 보상 트랜잭션으로 바뀌었다. 이론적으로는 우아하지만, 실제로 짜야 하는 코드의 양은 5배 가까이 늘었다.

  • 주문 생성 실패 시 재고 롤백 로직을 서비스마다 따로 구현
  • 결제 실패와 재고 부족이 동시에 발생하는 경쟁 조건 처리
  • 보상 트랜잭션 자체가 실패했을 때의 재시도 정책
"분산 시스템의 8가지 오류" 중 최소 5개를 우리 손으로 직접 재현해봤다.

3. 그래서 무엇을 다시 합쳤나

주문, 재고, 결제처럼 트랜잭션으로 강하게 묶여야 하는 7개 서비스를 하나로 합쳤다. 반대로 알림, 리포팅처럼 실패해도 재시도만 하면 되는 4개 서비스는 그대로 분리해뒀다. 모든 걸 나누거나, 모든 걸 합치는 것이 아니라 "트랜잭션 경계를 따라 나눈다"가 우리가 얻은 결론이다.
